# Подключение уже работающих сервисов

Инсталлятор не требует «чистого хоста». Уже работающие Jellyfin, Sonarr, Prowlarr,
Transmission и остальные определяются автоматически и **остаются как есть**;
compose поднимает только недостающие.

## Как работает обнаружение

`installer/discovery.py` опрашивает сервисы в таком порядке:

1. по **настроенному** `base_url` из `config_root/<сервис>.json` (если файл уже есть —
   так подключаются удалённые хосты и нестандартные порты/базовые пути);
2. по Docker-лейблам (`com.dubs.stack: dubs` — «managed by compose»);
3. по стандартным loopback-портам.

Никогда — по имени контейнера. Классы результатов (взаимоисключающие):

| Класс | Значение |
|---|---|
| `ready` | API отвечает, настроенные креды проходят |
| `needs-setup` | сервис работает, но креды отсутствуют/отклонены или открыт первичный мастер |
| `wrong-service` | на порту другой известный продукт (установка дубликата не предлагается) |
| `port-occupied` | порт занят, но известный продукт не отвечает |
| `unavailable` | ничего не слушает |

Каждый результат несёт флаги:

- `external: true` — настроенный `base_url` указывает **вне loopback**: сервис
  считается принятым, `install` его локально **не** ставит (в выводе `plan` —
  `external/adopted — will NOT be installed locally`);
- `managed: true` — контейнер с нашим compose-лейблом.

Посмотрите своё положение:

```bash
python3 -m installer plan --no-mutate
```

## Правила установки

- `install` поднимает через compose **только** сервисы в классе `unavailable`
  **без** флага external. Существующие приложения не перезапускаются и не
  перенастраиваются принудительно.
- Jackett и FlareSolverr — опциональный профиль `extras` (не входят в «core»).

## Настройка принятых сервисов

Соединения лежат в `config_root/` (по умолчанию `/etc/series-control`) в JSON вида:

```json
{"base_url": "http://192.0.2.10:8989", "key": "<API-ключ>"}
```

- `configure` создаёт скелеты с loopback-адресами; замените `base_url` на
  реальный адрес вашего существующего сервиса и вставьте ключ.
- Порты по умолчанию: Jellyfin 8096, Seerr 5055, Sonarr 8989, Radarr 7878,
  Lidarr 8686, Transmission 9091, Prowlarr 9696, Jackett 9117.
- Допустим и «легаси»-формат `{"port": 8989, "key": "..."}` (эквивалентно loopback).
- Для Transmission вместо `key` — `user` и `password`.

После заполнения снова `plan`/`doctor`: сервис должен перейти в `ready`.

### Удалённые сервисы и адреса

Внутри compose-стека приложения общаются по контейнерным именам
(`http://transmission:9091`, `http://prowlarr:9696`) — по умолчанию именно их
`bootstrap` прописывает в управляемые объекты. Если Sonarr/Radarr/Lidarr
работают **не** в локальном compose, контейнерные имена до них не резолвятся:
укажите явно **контейнерно-маршрутизируемый** внутренний адрес через
`DUBS_INTERNAL_<СЕРВИС>` в `compose/.env` (например
`DUBS_INTERNAL_RADARR=http://192.0.2.10:7878`) — тогда `bootstrap` впишет
именно его. Произвольные топологии сами собой не настраиваются: если ваши
сервисы не видят предложенный адрес из своей сети, поправьте управляемый
объект руками — адрес должен предоставить вы, оператор. Панель и автоматизации
на хосте используют `base_url` из `config_root` — они видят сервисы так,
как вы их указали.

## Пути хранилища при усыновлении

Стек предполагает единую схему путей: `/downloads` (в Transmission) — тот же
каталог, что `/torrents` (в Arr) и хостовый `MEDIA_ROOT/torrents`. Если
существующие сервисы используют другие пути, переопределите хостовые точки в
`compose/.env`-связанных переменных или в `config.json` → `paths`:

```json
"paths": {
  "shows_host": "/mnt/shows",
  "torrent_host": "/mnt/torrent",
  "sonarr_tv": "/tv",
  "sonarr_torrents": "/torrents",
  "downloads": "/downloads"
}
```

`bootstrap` создаёт remote-path mapping `transmission: /downloads/ → /torrents/`
только если для хоста mapping отсутствует; конфликтующий существующий mapping
он не перезаписывает и сообщает об ошибке — разрулите вручную.

## Sentinel хранилища

Compose-стек требует «вооружённый» sentinel (`.dubs-storage-ok`). Если вы
приняли существующие сервисы и compose-стек для хранилища вообще не используется,
можно отключить требование в `config.json`:

```json
"storage_sentinel": false
```

Само хранилище при этом обязано существовать и быть смонтированным — `doctor`
и `check` продолжают проверять `storage_ready` (статvfs + sentinel-кандидаты).

## Что bootstrap не делает с принятыми сервисами

Создаются/обновляются только объекты с управляемыми именами:
`Dubs RU 2160p`, `Dubs RU 1080p`, `Озвучка NN — …`, `Русская дорожка / RU`,
`Dubs Transmission`, `Sonarr/Radarr/Lidarr (Dubs)` в Prowlarr, импорт-лист
`MyShows watching (Dubs feed)`. Ваши собственные профили, клиенты, индексаторы
и списки остаются нетронутыми; чужой объект с именем «Transmission» игнорируется.
